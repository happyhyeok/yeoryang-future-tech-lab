# 저장 응답 timeout과 실제 서버 저장 상태 불일치

작성일: 2026-09-22
우선순위: 중간
상태: 백로그 — 미구현

## 현상

test01 Day05 E2E에서 `saveDayRecord` 요청이 전송됐지만 클라이언트의 8초 제한이 먼저 만료되어 `AbortError` 및 저장 실패 안내가 표시됐다. 이후 분리된 저장 영역에서 서버 기록을 다시 조회하자 같은 검수 입력값과 선택 이유가 복원됐다. 따라서 클라이언트 요청이 timeout됐더라도 서버 작업은 계속되어 기록이 저장될 수 있다.

## 위험

현재 UI가 `저장하지 못했어요`라고 표시해도 서버에는 이미 반영됐을 수 있다. 학생은 저장 실패로 오해해 불필요하게 재시도할 수 있고, 화면의 저장 상태와 실제 서버 상태가 일시적으로 달라질 수 있다. 반대로 서버 반영 여부를 확인하지 않고 성공으로 표시해서도 안 된다.

## 현재 상태

- 이번 test01 E2E에서 데이터 유실은 확인되지 않았다.
- 분리된 저장 영역의 server restore와 Day06 `projectReload`에서 해당 test01 기록을 확인했다.
- `saveDayRecord` 클라이언트 응답은 timeout됐으므로 응답 성공 자체를 확인한 것은 아니다.
- 지금은 timeout을 실패 안내로 처리한다. timeout만으로 실제 서버 반영 여부를 판정할 수 없다.
- 이번 백로그 기록 단계에서는 저장 코드나 Apps Script를 변경하지 않는다.

## 향후 해결 후보: save reconciliation

1. `saveDayRecord` 응답 timeout 시 즉시 최종 실패로 확정하지 않고 `저장 결과 확인 중...` 상태를 보여준다.
2. 잠시 후 동일 학생·연구일의 `getDayRecord`를 재조회한다.
3. 서버 record의 revision/`updatedAt` 및 저장 payload를 비교한다.
4. 서버 반영이 확인되면 `✓ 저장됨`으로 전환한다.
5. 반영되지 않았음이 확인되면 `저장하지 못했어요 / 다시 시도`를 안내한다.
6. 조회도 불확실하게 끝나면 성공이나 실패로 단정하지 않는 보류 상태를 유지하고 재확인 방법을 제공한다.

위 순서는 후보 설계이며 확정 구현 사양이 아니다. 재조회 API와 서버 스키마가 실제로 제공하는 비교 가능한 version 필드를 먼저 확인해야 한다.

## 구현 전 검토 항목

- `localRevision`, `localUpdatedAt`, `serverUpdatedAt`, `serverSyncPending`의 생성·증가·복원 규칙
- 서버 `updatedAt` 해상도와 record revision/version 유무
- 학생 변경 중 이전 학생 응답이 도착하는 경합
- Day 변경 또는 화면 이탈 뒤 늦은 응답이 도착하는 경합
- 빠른 연속 수정 시 오래된 응답이 최신 상태를 덮는 문제
- 동일 payload 재전송의 멱등성 및 중복 저장 위험
- 요청 상관관계용 `requestId`를 기존 계약에서 지원하는지
- 재조회 요청의 timeout/retry 횟수와 오프라인·서비스 장애 UX
- Apps Script 동시 실행, quota, 읽기 지연 및 추가 부하
- 다른 연구일·다른 학생 기록을 절대 섞지 않는 server-side scope 검증

## 완료 조건 후보

- 서버가 기록을 반영한 뒤 클라이언트 응답만 timeout된 상황에서 재조회가 해당 revision을 확인하고 성공 상태로 수렴한다.
- 반영되지 않은 저장은 성공으로 표시하지 않고 안전하게 재시도할 수 있다.
- 학생/연구일을 바꾼 뒤 도착한 이전 응답은 현재 화면 상태를 바꾸지 않는다.
- 느린 응답, 중복 입력, 오프라인, Apps Script 실패 상황에서 데이터와 UI 상태가 일관된다.
- test01 전용 데이터로 저장 → 새 저장 영역 서버 복원 → 화면 상태 확인 E2E를 통과한다.

## 우선순위 근거

중간. 이번 검수에서는 실제 데이터 유실이나 수업 진행 차단은 확인되지 않았다. 다만 저장 상태 UI 신뢰도와 재시도 혼란에 직접 관련되므로 추후 해결이 필요하다.
